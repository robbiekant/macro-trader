# How the Harness Works

**Agent = model + harness.** The model supplies judgment. The harness is everything around it: what each agent is told, what it can see, which tools it may call, how its output is checked, where state lives, what it is forbidden to do, how every step is recorded, and how the system learns. In a trading system the harness matters more than the prompt, because the harness is what keeps a confident wrong answer from becoming a loss.

This document explains the eight harness subsystems and how one run moves through them. Each subsystem maps to concrete files or tables in this repository.

---

## The two control types

Harness controls come in two directions and two flavors.

| | **Computational** (deterministic code, cheap, always on) | **Inferential** (another model judges) |
|---|---|---|
| **Guides** (feedforward: steer before the agent acts) | Typed tool signatures, allow-listed tools, context packs built by code, JSON output schema, policy limits stated in the prompt | Agent charters, playbooks, accepted lessons from past post-mortems |
| **Sensors** (feedback: check after the agent acts) | Schema validator, citation checker, freshness checker, numeric consistency checks, policy engine, stress engine | Red Team review of the CIO plan, Risk Manager memo, Janitor drift review, your approval |

Rule of thumb used throughout: **prefer a computational control whenever the rule can be written down.** Inferential controls are for questions that need judgment.

## The eight subsystems

### 1. Instructions and context (guides)

- **`AGENTS.md` is a map, not a manual.** It is short and points to deeper documents. Agents and humans load detail only when needed (progressive disclosure).
- **One charter per agent** (`harness/agents/charters/<id>.md`, versioned in git): mission, the questions to answer, tools allowed, output contract, definition of done, and what is forbidden. The mission text in `config/agents.yaml` is the seed.
- **Context packs are built by code, not by the agent.** Before a step, the harness compiles a bounded pack (≤ 30k tokens) from Postgres: a summary table of the agent's series (last value, 1m/3m/12m change, z-score, percentile, staleness flag), its own previous report, accepted lessons, upcoming events, and the relevant playbook excerpt. Raw history is available through tools for drill-down, not pasted in.
- **Prompt layout for caching:** charter + golden rules + tool definitions form a frozen prefix (cached); the context pack and run-specific data come after the cache breakpoint. Nothing time-varying goes in the prefix.
- The pack is hashed and the hash is stored on the step (`ops.agent_step.context_pack_hash`), so we can always reproduce exactly what an agent saw.

### 2. Tools (least privilege)

- **Research agents are read-only.** They can read series, metrics, prices, curves, vol metrics, documents and their own history. They cannot fetch from the internet's data APIs; if something is missing they file a `data_request` that the Data Steward queues.
- **Web access is narrow.** Only geopolitics, supply chain, energy, metals and rates may use web search/fetch, only on allow-listed domains, and every fetched page is archived to `research.document` with a hash so it is never fetched twice.
- **Numbers come from tools.** Statistics, option prices, Greeks, sizing, buying power and stress losses are tool outputs. Agents never do arithmetic that matters in their head.
- **The structurer can only pick `candidate_id`s** generated by code from live chains. It cannot type a strike or a price.
- **No LLM can reach the broker.** Orders are placed only by the Execution Gateway, for tickets that passed risk and that you approved.
- Every tool call, allowed or blocked, is logged in `ops.tool_call`. A blocked call returns an error message that says why and what to do instead.

### 3. State and memory (system of record)

- **Postgres is the single source of truth** (`db/schema/001_core.sql`). If a fact is not in the database with provenance, agents treat it as unknown.
- **Three memory tiers:**
  - *Working memory:* the context pack for this step.
  - *Episodic memory:* the agent's previous reports and their outcomes (`research.report`, `research.view`).
  - *Semantic memory:* lessons accepted by you after post-mortems (`ops.lesson`, status `accepted`), plus the playbooks in git.
- **Runs are checkpoints.** Each run and each agent step is a row; a crashed run resumes from the last completed step. Re-running a step with the same inputs is idempotent.
- **Point-in-time correctness.** Every observation carries a vintage date, so a replay as of any past date sees only what was known then.

### 4. Orchestration (code controls the flow)

The control flow is a fixed DAG in code. Models decide *what to conclude*, never *what runs next*.

```
weekly_ic(as_of):
    preflight()                   # kill switch, broker link, budgets, critical data freshness
    steward.ingest_due()          # downloads only due deltas
    steward.recompute_derived()   # CAPE percentiles, net liquidity, vol metrics
    reports = parallel(research_agents, step)          # 11 agents, each sandboxed
    prior   = regime_model(reports)                    # deterministic
    regime  = step(regime_strategist, prior)           # bounded ±15 pt adjustment
    plan    = step(cio, regime, reports)
    review  = step(red_team, plan)                     # separate context
    plan    = step(cio, plan, review)                  # must answer each challenge
    tickets = step(options_structurer, plan, candidates(plan))
    verdict = policy_engine(tickets, portfolio)        # block is final
    memo    = step(risk_manager, verdict)              # can only shrink or reject
    await human_approval(tickets)                      # dashboard
    execution_gateway.submit(approved)                 # paper by default
    post_run_report()

step(agent, inputs):                                   # one agent step
    pack = build_context_pack(agent, inputs)
    for attempt in 1..3:
        out = run_agent_loop(agent.charter, pack, agent.tools, budget=agent.budget)
        results = [schema(out), citations(out), freshness(out), numbers(out), policy(out)]
        if all(results.passed): return store(out, status="validated")
        pack = append_remediation(pack, results)       # appended as a new turn; history is never edited
    mark_failed(agent); degrade()                      # e.g. reuse last week's report, flagged stale
```

Budgets per step (tool calls, dollars, wall-clock) are enforced by the runner. A run that exceeds its dollar budget stops and opens an incident.

### 5. Verification (sensors)

| Sensor | Checks | On failure |
|---|---|---|
| Schema | Output matches `contracts/*.schema.json` | Remediation message listing the exact fields |
| Citation | Every number in a finding resolves to a stored observation, metric or document, and the cited value matches the database within tolerance | Remediation naming the bad citation |
| Freshness | Every series in `data_used` is within its freshness rule for this run | Remediation, or the claim is dropped |
| Numeric consistency | Signals agree with the stance; probabilities sum to 1; views have machine-checkable resolution rules | Remediation |
| Policy engine | Every proposal and the post-trade book against `config/risk_policy.yaml` | `block` is final; `warn` goes to the Risk Manager |
| Red Team | Inferential review of the CIO plan | CIO must answer each challenge in writing |
| Human | You approve, modify or reject each ticket | Nothing executes without it |

### 6. Guardrails and permissions

- **Hard limits outside the model.** Limits are YAML enforced by code. The prompt tells agents the limits (a guide), but compliance is checked by the policy engine (a sensor). Agents cannot edit `config/`.
- **Modes:** `research` (no proposals), `paper` (default), `live` (requires an explicit config change you make, and still needs per-ticket approval).
- **Circuit breakers** on drawdown, daily loss, VIX level, stale critical data and run cost.
- **Kill switch** checked before every run and every order.
- **Idempotent execution:** each order has a unique idempotency key so a retry can never double-fill.

### 7. Observability and lineage

- Every run, step, tool call, token count, cache hit and dollar is recorded (`ops.run`, `ops.agent_step`, `ops.tool_call`).
- **Lineage from trade to byte:** order → proposal → research reports → evidence rows → series observations → fetch log → raw payload hash. The dashboard's Lineage page walks this chain.
- The Harness Ops page shows validation failure rates per agent, blocked tool calls, retries, cost per run and data freshness, so problems are visible before they become losses.

### 8. Evals and the learning loop

- **Golden replays** (crisis dates in `ops.eval_case`) run on every change to prompts, tools or policy. They check behavior: breakers fire, limits hold, no banned structures, no data from after `as_of`.
- **Calibration:** every view is a falsifiable forecast with a resolution rule. The Performance agent resolves them and keeps a Brier score per agent. Agents whose views add nothing get less weight in the CIO's synthesis.
- **Post-mortems → lessons:** after losing trades or missed regime turns, the Performance agent proposes a lesson; you accept or reject it; accepted lessons enter the relevant agents' context packs.
- **Entropy control:** the Janitor runs weekly to find failing adapters, TTLs that are too short (fetches that return no new rows), contract or doc drift, unused series and cost creep, and proposes small fixes as PRs.

## Runtime: the harness inside Claude Code

The harness runs in Claude Code cloud sessions on your Pro plan (`config/runtime.yaml`). Claude Code supplies the agent loop; this repository supplies everything else.

| Harness subsystem | How it is realized in Claude Code |
|---|---|
| Instructions & context | `AGENTS.md` (loaded via `CLAUDE.md`), one `.claude/agents/<id>.md` sub-agent per agent, context pack passed in the step prompt |
| Tools | A local MCP server (`harness/mcp/`) exposes only read-only database tools and `submit_report`; `--allowedTools` limits each step to them (plus web tools for the five web desks); scheduled tasks attach no claude.ai connectors |
| Typed output | `--json-schema contracts/<contract>.schema.json`; `submit_report` re-validates schema and citations against the database and returns remediation text on failure |
| Orchestration | Python DAG runs one `claude -p` per agent step, so code, not the model, decides what runs next |
| Guardrails | `--permission-mode dontAsk` and `--permission-prompts none` deny anything not allow-listed; hooks log every tool call to `ops.tool_call`; risk limits and the paper broker are plain code no agent can call |
| Observability | `--output-format json` returns session ID, usage and an API-equivalent cost estimate per step, stored in `ops.agent_step` |
| State | Supabase Postgres; the cloud container is disposable |
| Budget | Weekly work split into three sessions in separate five-hour windows; checkpoints let a run resume after a usage-limit reset |

## Golden rules

1. Models judge; code computes, controls the flow and enforces limits.
2. If it is not in the database with provenance, it does not exist.
3. Only the Data Steward talks to external data APIs, and it never downloads the same thing twice.
4. Every number an agent states cites stored evidence, and the citation is checked.
5. Every output is a typed contract; invalid output is sent back with a remediation message, never silently repaired.
6. Each agent gets the fewest tools that do its job; research agents are read-only; no model can reach the broker.
7. Risk limits live in versioned config, enforced by code, changed only through a reviewed PR.
8. You approve every trade until you explicitly decide otherwise.
9. Replays are point-in-time; no look-ahead.
10. Every step is observable and reproducible from its stored context hash.
11. Every view is falsifiable and gets scored.
12. Clean up drift continuously, in small changes.
